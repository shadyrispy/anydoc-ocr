候选 1：批处理入口 + 跨文档引擎复用

Strong
涉及：src/main.rs · src/convert.rs · src/ocr_engine.rs

问题：convert_to_markdown(&Path) 是单文件 API；CLI main.rs 只接一个 input。处理 N 个 PDF = N 次进程启动 = N 次模型冷加载（实测 0.5s/进程）+ N 次 ORT 全局线程池初始化。OcrEngine 的 static CACHE 是进程级——它本来就是为跨调用复用设计的（注释写明"跨文档/跨调用复用"），但单文件 CLI 让它永远只命中一次就随进程退出。这是多文档吞吐的最大杀手：100 个文档凭空多 50s 纯模型重载。

方案：引入 BatchConverter 深模块，持有 Arc<OcrEngine> 句柄（一次性 build）+ 跨文档调度。CLI 加 --batch <dir> 或接受多个 input 路径。库 API 加 convert_many(paths, opts) -> Vec<Result<String>>，内部复用同一 engine 实例。MinerU 的 AtomModelSingleton + -p dir 即此模式。

收益（locality + leverage）：模型加载与 ORT 初始化的复杂度收敛到 BatchConverter 一处（locality）；调用方只需传 paths 列表即拿到 N 份 markdown，不重复付冷启成本（leverage）。测试面改善：可单测 convert_many 传 3 个 paths 验证 engine 只 build 一次（用计数器 mock）。

删除测试：删掉 BatchConverter，多文档只能逐个 convert_to_markdown，每次 build engine——N 次冷加载复杂度重现 → earning its keep。

候选 2：跨文档流水线（PagePipeline 升档）

Strong
涉及：src/pipeline.rs · src/pdf/mod.rs · src/ofd/mod.rs · src/pdf/render.rs

问题：PagePipeline 是 per-document：每个 doc 自己 spawn render 线程 + rayon scope + channel。处理很多小 PDF（1-3 页）时，per-doc setup 开销（thread spawn、channel 创建、rayon scope 建立）+ 文档边界处 OCR 池空转 dominates。doc1 OCR 跑完 → pipeline 结束 → doc2 重新 spawn → render 线程冷启。MinerU 的 doc_analyze_streaming 把多文档页面打包进同一 64 页处理窗口，文档边界只是 idx 跳变，pipeline 不停。

方案：把 PagePipeline 从"per-doc 流水线"深化为"跨文档流水线"——一个长期运行的 render↔OCR pipeline，喂入 (doc_idx, page_idx, img)，产出 (doc_idx, page_idx, StructureResult)。RenderFn 升级为可跨文档迭代（接受 paths 列表，内部逐 doc open + 逐页渲染，idx 连续编号）。文档边界只是 idx 跳变，render 线程和 OCR 池都不停。

收益：文档间 OCR 池空转消除（locality：调度逻辑集中到 pipeline 一处）；小文档 setup 摊薄（leverage：调用方传 paths 列表即拿到连续页结果）。依赖候选 1 的 BatchConverter 提供 engine 句柄。

BEFORE — per-doc pipeline，边界空转
doc1: render→OCR→gfm
空转（teardown + setup）
doc2: render→OCR→gfm
空转
doc3: render...
AFTER — 跨文档 pipeline 不停
render d1p1→OCR d1p1
render d1p2→OCR d1p2
render d2p1→OCR d2p1 [边界不停]
render d2p2→OCR d2p2
render d3p1...

删除测试：删掉跨文档 pipeline，回到 per-doc pipeline——文档间 OCR 池空转、小文档 thread spawn 开销重现 → earning its keep。

约束：PDFium PdfDocument 非 Send、OFD OfdReader 非 Send——render 仍须在专属线程，闭包内逐 doc open（ADR-0002 已确立此模式，跨文档版本沿用）。RenderItem 的 idx 升级为 (doc_idx, page_idx) 复合键。

候选 3：页级批推理（OCR 消费端攒批）

Worth exploring
涉及：src/pipeline.rs（OCR 消费段）· src/ocr_engine.rs

问题：pipeline 里 engine.analyzer.predict_images(vec![img]) 单页喂——oar-ocr 支持 batch，但当前一页一喂（为了流水线掩盖渲染延迟）。CPU 推理（飞腾场景）单页 kernel launch + 内存搬运开销没摊薄。MinerU 用 batch_ratio × BASE 一次推多页（OCR det 一次 8×ratio 张）。

方案：OCR 消费端攒一个小 buffer（如 4 页），凑够或超时即 predict_images(buffer)。需平衡：攒批提高吞吐 vs 延迟流水线掩盖渲染。MinerU 的处理窗口（64 页）在 GPU 上收益巨大，CPU 上收益待测。

收益：摊薄 ORT 单次推理开销（locality：攒批逻辑在 pipeline 内）。但 CPU 场景 batch > 4 后内存峰值上升 + padding 浪费反噬，需实测。

⚠️ ADR-0002 关联风险：ADR-0002 已记录"单页 predict_images(vec![img]) vs 批量存在数值级差异（oar-ocr batch padding/resize 影响），multipage.pdf golden 已 UPDATE 重基线"。改 batch size 需重新 ANYDOC_GOLDEN_UPDATE=1 重基线，且不同 batch size 间结果可能漂移——golden 锁的是某个固定 batch。建议先实测 batch=2/4 的吞吐收益与精度变化再决策。

删除测试：攒批模块删掉后 OCR 回到单页喂——功能不破，只是丢吞吐优化。删掉复杂度不重现（单页喂更简单）→ 这个深化是 leverage 型而非 locality 型，ROI 取决于实测收益是否值得 golden 重基线成本。

候选 4：OCR 引擎预加载与文字层预检解耦

Worth exploring
涉及：src/pdf/mod.rs · src/ofd/mod.rs · src/pipeline.rs（P4 预加载半成品）

问题：convert_pdf 内：先 text_layer_markdown（文字层判定，含 0.3s deep garbled 检查）→ 判定走 OCR → 才 OcrEngine::build。对纯图片型文档批量，每文档都要先做一次注定失败的文字层预检 + 串行 build。MinerU 模型在进程启动即加载。pipeline.rs 注释提到 P4 预加载但没完全实现（"engine 已由调用方 build，预加载收益在首文档"——半成品）。

方案：detect 阶段或批处理入口即 spawn 后台 OcrEngine::build，与首文档文字层预检并行。在候选 1 的 BatchConverter 构造时就触发 build，首文档预检期间模型已在后台加载。

收益：首文档冷加载 0.5s 被文字层预检掩盖（locality：预加载逻辑收敛到 BatchConverter 构造）。单文档场景收益小，多文档场景首文档延迟降低。

BEFORE — 串行
text_layer 预检 (0.3s)
build engine (0.5s)
OCR
AFTER — 预加载并行
text_layer 预检 (0.3s)build engine (0.5s) ‖
OCR [engine 已就绪]
首文档省 ~0.3s

删除测试：删掉预加载，build 回到 convert_pdf 内串行——首文档多 0.3s。复杂度小，主要是"把 build 提前 + spawn"的工程改动，ROI 中等。

候选 5：GFM 输出流式（producer-consumer）

Speculative ADR-0003 已预见
涉及：src/gfm_adapter.rs · src/emitter.rs

问题：ADR-0003 已记录"双段先做，GFM 流式延后，待 P7 per-page 计时实测占比再定"。当前 GFM 是 OCR 后批量串行收尾（structure_results_to_gfm(&pages)）。多文档场景下，doc N 的 GFM 收尾时 doc N+1 的 OCR 停转。MinerU 用 ThreadPoolExecutor(max_workers=1) 后台输出。

数据不支持：本机 bench 显示 GFM 阶段 3–8ms，占比 < 1%（multipage 8 页 gfm 8.5ms / 总 7060ms）。ADR-0003 的"延后"决策被实测验证正确。改 gfm_adapter 签名（batch→stream）+ DocumentEmitter 线程安全的风险，远高于 <1% 的潜在收益。

结论：不建议做。列出仅为记录"已评估并排除"。若未来单文档页数极大（>100 页）使 GFM 占比上升，或加 JSON 输出需 per-stage golden，再重新评估。

ADR-0003 关联：此候选即 ADR-0003 延后的"P5 GFM 流式"。本评审用实测数据（gfm <1%）验证了 ADR-0003 的延后决策。不构成 ADR 冲突，反而是 ADR 的数据回填。

🏆 Top 推荐

候选 1 + 候选 2 组合，按此顺序。

  1. 先做候选 1（批处理入口）——这是前置依赖。单文件 CLI 是多文档吞吐的根本瓶颈：N 进程 = N×0.5s 模型重载 + N×ORT init。convert_many + --batch 让 OcrEngine 的进程级 cache 真正发挥作用（它本来就是为跨文档复用设计的，被 CLI 架构拖累）。100 文档省 ~50s 纯开销，零精度风险（不改 OCR 路径）。
  2. 再做候选 2（跨文档流水线）——在候选 1 的 BatchConverter 上把 PagePipeline 升档为跨文档。消除文档边界 OCR 池空转 + 小文档 setup 摊薄。这是 MinerU doc_analyze_streaming 的核心。需处理 RenderItem idx 升级为复合键，但 render 仍专属线程（ADR-0002 模式不变）。

候选 3（批推理）作为可选增量，但需先实测 batch=2/4 的吞吐收益与精度漂移，并接受 golden 重基线成本（ADR-0002 已预警）。候选 4（预加载）在候选 1 落地后自然收敛到 BatchConverter 构造时，作为候选 1 的附属实现。候选 5不做（ADR-0003 数据已验证）。

组合落地后，多文档吞吐从"N×(冷启 + per-doc pipeline setup + OCR)"降到"1×冷启 + 跨文档连续 pipeline + OCR"，对齐 MinerU 的单进程批处理 + 跨文档处理窗口模式。
